# Adding the PDP-11/05 to the microcode window

An action plan. **Phases 1 to 5 and 7 are done** - see "Where this stands" at the end - and what
is left is the hardware check in phase 6 and the optional prose annotations in phase 4. The rest
of this file is kept as it was written, because it is the reasoning that produced the code and
several of its claims are now assertions in `Kd11bMicrocodeTest`.

The original preamble: the microcode window today shows the PDP-11/44's microcode and nothing
else; this is what it takes to make it show the 11/05's (KD11-B) as well, in what order, and
which decisions have to be taken before which code can be written.

Read `CLAUDE.md` and `PLAN.md` §6 first; the rules there apply to all of it, in particular that
the decoding is `pdp11-core` with tests and the window only shows its result.

## Where the 11/44 support lives

Three layers, and only the third is reusable as it stands:

| Layer | Files | 11/05 reuse |
| --- | --- | --- |
| Field table | `pdp11-core/.../microcode/MicrocodeField.java` | none — new table, and the class has to stop being static |
| Listing format | `MicrocodeLineParser.java`, `Pdp1144Microcode.java` | the container yes, the parser no |
| The window | `pdp11-ui/.../microcode/Microcode{Panel,TableModel,Window}.java` | nearly all of it |

The static coupling that has to go is small — four production call sites:
`MicrocodeLineParser.java:108`, `:120`, `:121` and `MicrocodeTableModel.java:48`, all of them
reaching for `MicrocodeField.ALL` or `NEXT_ADDRESS`.

## What is settled

- **The control store is 256 microwords of 40 bits**, held in 256×4 PROMs (74187, 82S126,
  6300 and equivalents) — ten 4-bit slices per microword.
- **The microword carries a full explicit 8-bit next-address**, plus 4 bits of branch microtest
  (BUT) and 5 bits of ALU control; the remaining ~23 bits are the rest of the control lines.
- **That 8-bit next-address is `MPC0..MPC7` on the KM11**, which is confirmed independently by
  `~/km11-signals.txt` — the Km2 column of the KM11 being built for this machine.
- **So `MicroInstruction` does not have to change shape.** Next-address explicit in the word with
  BUT as the hardware branch overlay is structurally the same as the 11/44's
  `NEXT MICROWORD ADDRESS` + `BUT ENABLE`: `getNextAddress()`, the fall-through predecessor index
  and the Next button all carry over. This was the one open question that could have forced a
  redesign, and it did not.
- **The bits are transcribed, and they came from the listing rather than from a dump.** The
  drawing sets contain the *microcode listing* pages — symbolic tag, octal address and all 40
  bits under named field headings — not PROM images. That is a better source than a dump and it
  removes phase 3's slice-map risk entirely. See `~/1105rom/derived/kd11b-README.md`.
- **The listing has 214 microwords, not 256.** The other 42 control-store locations are simply
  not printed. Both drawing sets agree on this exactly.
- **The field table is done.** `~/1105rom/derived/kd11b-fields.tsv` gives, for all 40 bits:
  listing label, listing column, schematic bit number, signal name, polarity and the PROM part
  number in each revision. The layout read off the dash rule and the bit map read off the M7261
  schematics (`~/1105rom/pdp-1105-microcode.txt`, from `EK-KD11B-MM-001`) **agree on all 40 positions**;
  the listing prints schematic bit 39 leftmost, so `LISTCOL = 39 - SCHBIT`. The fifth ALU bit,
  which has a dash but no heading letter, is `ALU-MODE-H`.
- **Polarity is known per bit, from the signal names.** `-L` signals are asserted low, `-H` high.
  That is what `MicrocodeField` needs for defaults, and it is why `AUX`, `PSW`, `DIP` and `ABT`
  are 1 in 94–97% of microwords: they are `AUX-CONTROL-L`, `LOAD-PSW-L`, `ENAB-IN-PAUSE-L` and
  `ALLOW-BYTE-L`, sitting inactive.
- **The `ALU` field decodes completely**, against the operation table in the manual: all 12
  distinct codes are named operations and they cover 214 of 214 microwords, with the printed bits
  used as-is. `AL` 105, `BL` 48, `A plus B` 21, `ASR` 16, `A-B-1` 9, `not A` 8, and six singletons.
- **Every field has symbolic value names**, in `~/1105rom/derived/kd11b-fieldvalues.tsv`, keyed
  by the *printed* bit pattern so the two scrambled fields cannot be got wrong. `BUT` uses all 16
  microtests (`NON` in 141 of 214, and exactly one `IR-DECODE` in the whole microprogram);
  `BRG` is `HOLD`/`LOAD`/`SLEFT`/`SRIGHT`; `TNS` is `NONE`/`DATI`/`DATO`; `ALG` selects the A leg;
  `SPAMUX` selects where the scratchpad address comes from. **This is the `MicrocodeField` value
  table for the KD11-B** — names, widths, positions, polarity and value names, all of it.
- **`AUX` is `AUX-CONTROL-L`, and it changes what the `ALU` field means.** It selects whether
  `ALU S0..S3`, `ALU MODE` and `CIN` come from IR bits 15..12 (`AUX=0`) or IR bits 10..6
  (`AUX=1`), through decode PROMs — the double-operand and single-operand opcode fields. So in
  those microwords the ALU operation is decoded from the *instruction*, which is how one
  microword executes `MOV`/`CMP`/`BIT`/`BIC`/`BIS`/`ADD`/`SUB` alike. **Consequence for the
  window: where `AUX` is asserted the printed `ALU` field may be a don't-care and must not be
  shown as what the machine does.**
- **The E→F revision is legible now, and it is a design change.** Rev E asserts `AUX` in six
  microwords, all `not_A`; rev F asserts it in nine, none of them the same ones — the set moved
  wholesale. Six of them (`MB-0`, `U1-1`…`U5-1`) changed `AUX` and `CKO` *together*, and those
  two bits live in two different PROMs. A coordinated change across two chips is why both part
  numbers changed. Table in `kd11b-README.md` §6.
- **`FSH` (bit 25) is `F-SHIFT-L`, the shifter on the ALU output** — the schematics name it, and
  the data proves it. It is asserted in 35 microwords which form **five straight-line chains of
  exactly seven consecutive shift steps**, each holding one ALU code and one B-leg select for all
  seven and stopping on the eighth. Across all 214 microwords it appears with only two of the
  twelve ALU codes, `AL` and `ASR`. That also explains why `ROL` and `ROR` are in the manual's
  operation table but in no microword: the rotates are not ALU functions, the ALU passes a leg
  through and `F-SHIFT` does the shifting. `A xor B` is absent for a different and satisfying
  reason: **the 11/05 has no `XOR` instruction**, which arrived with the 11/45. With `BRG` decoded
  the chains read completely —
  `DO-1..7` and `SBO-1..7` are `AL` + `SLEFT`, `DO-11..17` is `AL` + `SRIGHT`, and `SB1`/`SB2` are
  `ASR` + `SRIGHT`. Three fields decoded independently, agreeing.
- **Two traps the listing sets.** `ROM-SPA-0..3`, the scratchpad register address, is printed as
  four *non-adjacent and out-of-order* single-bit columns (`SP0`@21, `SP1`@17, `SP2`@27,
  `SP3`@18); assembled it reads as register numbers, 7 (PC) in 28 microwords and 6 (SP) in 22.
  And the `BUT` nibble is scrambled — printed left to right it is `BUT-1, BUT-0, BUT-2, BUT-3`.
  A field table that treats either naively shows nonsense. The `.tsv` ships `SPA` assembled.
- **`NXT` is stored active low: the next microaddress is `NXT XOR 0377`.** Established by test —
  as printed, 83.2% of next-addresses hit a listed location, which is chance level since 214 of
  256 are listed; complemented, 99.5% hit one, and the chain reads
  `B-1 @015 -> 147 = B-2 -> 146 = B-3 -> 040 = BG-1`. The schematics then confirmed it outright:
  the signals are `MPC-0-L` … `MPC-7-L`. This is exactly the class of silent error phase 6 was
  written to catch, and it would have gone straight into the field table unnoticed.

- **Which revision each set is, and how to tell on the bench.** The 1973 set is **M7261 rev E**
  and the 1976 set **rev F**. The listings differ in **20 bits across 14 microwords, confined to
  two control lines, `AUX` and `CKO`** — `~/1105rom/derived/kd11b-revision-diff.txt` lists them.
  The schematics confirm that independently and exactly: of the ten control-store PROMs, **two**
  change part number between E and F, bits 8–11 (`23A14A2` -> `23A19A2`) and bits 24–27
  (`23A15A2` -> `23A20A2`). `CKO` is bit 11 and `AUX` is bit 24, so the two PROMs that change are
  precisely the two holding the two fields where the transcriptions differ, and no difference
  appears in any of the other eight. OCR of printed bits and part numbers on a schematic are
  about as independent as two sources get.

  **So the machine does not have to be running to decide this: read the part numbers off the two
  PROMs.** `23A14A2` + `23A15A2` is rev E and takes the 1973 listing; `23A19A2` + `23A20A2` is
  rev F and takes the 1976 one.
- **Which PROMs are control store**, which was open when the source was expected to be a dump.
  All ten are named in `kd11b-fields.tsv` with the bits they carry, at E092–E107 on a rev E board
  and E102–E116 on a rev F one. Everything else on M7260/M7261 is random-logic replacement and is
  not microcode. Nothing needs to be loaded from a PROM anyway — the listing is the source — but
  this is what makes the bench check above possible.

## What is not settled

- **`CKO`'s exact condition.** It is `CKOFF-L`, the processor clock stop, sitting among the
  `MSYN`/`SSYN` bus signals — but the listing alone does not say precisely when it is asserted:
  22 of the 36 `CKO=0` microwords start a bus cycle and 14 do not, and 17 microwords start a
  `DATI` without it. The value-name polarity in the notes also reads backwards against the data.
  See `kd11b-README.md` §6.
- **Two smaller gaps**, both recorded in `kd11b-README.md` §10: `BTP=1, BBT=0` occurs in 26
  microwords and the schematic notes do not name that combination; `IRS` versus `IRD` in `SPAMUX`
  cannot be told apart by the data, since they are the two values that swap when the mux bits do.
- **What the five seven-step shift chains are for.** `F-SHIFT` is asserted in exactly five
  straight-line runs of seven (`DO-1..7`, `DO-11..17`, `SB1-1..7`, `SB2-1..7`, `SBO-1..7`), each
  stopping on its eighth microword. Seven shifts ending on an eighth step looks byte-wide, and
  the naming suggests shift-out/shift-in routines, but that is a guess.

## Phase 0 — decisions, before any 11/05 code

All four of the original questions are **gone**. The source is a listing, not a dump, so there is
no slice map and no "which images are control store"; the tags came with the bits; the polarity is
in the signal names in `kd11b-fields.tsv`.

And **"which revision" is not a decision either — it is a user choice.** There are rev E and rev F
M7261 boards for this machine and either can be in the rack on any given day, so the window has to
ship both microcodes and let the user say which one it is looking at. See phase 5.

What is left is only a first-run default, which the settings then remember. Take **rev F**: it is
the later board and the better scan. Nothing depends on getting that right, because the setting
overrides it on the second run.

Phase 0 no longer gates anything. Phase 1 can start immediately.

## Phase 1 — make the core architecture-independent

No behaviour change, no new data; the 11/44 output must be identical before and after.

- Introduce `MicrocodeFields` (or `MicrocodeArchitecture`): an object holding the field list, the
  next-address field, the name index and the identity index that `MicrocodeField.index()` uses
  today. **Note that a revision is not an architecture.** Rev E and rev F have identical field
  tables and differ only in 20 data bits, so one `MicrocodeFields` instance serves both; the
  revision belongs to the loaded `Microcode`, as a label it carries and can be asked for. `MicrocodeField.ALL`, `NEXT_ADDRESS`, `byName` and the static `INDEX` map go away;
  `Pdp1144Fields` becomes one instance of it.
- `MicroInstruction` carries a reference to the field table it was decoded against, so
  `getValue`, `getText` and `isDefault` still work and the table model can walk `mi.getFields()`
  rather than a static list.
- Rename `Pdp1144Microcode` to `Microcode` and parameterise it by architecture. Everything in it
  except `builtin()` and the listing-specific line rules is already generic: the three sort
  orders, the address/tag/line indexes, the predecessor map, `Problem` collection and
  `describe()`.
- Let the architecture supply its own cross-checks. `verify()` as written is about the 11/44
  listing's redundancy (`MISSING_NEXT`, `JUMP_NOT_IN_SOURCE`) and does not apply to a PROM dump.
- Adjust the four call sites above, plus `MicrocodePanelTest.java:78` and
  `Pdp1144MicrocodeTest.java:103,307,322-329` in the tests.

The whole of `Pdp1144MicrocodeTest` must still pass unchanged in meaning: it is the proof that
the refactor moved nothing.

## Phase 2 — get the data in, with its provenance

Largely **done**, in `~/1105rom/derived/`, with the pipeline that produced it in `~/1105rom/ocr/`.
What remains is to move it into the tree:

- Put `kd11b-microcode-1973.tsv` and `kd11b-microcode-1976.tsv` under
  `pdp11-core/src/main/resources/microcode/kd11b/` — **both, always, because both are
  selectable at runtime** — with `kd11b-fields.tsv` and `kd11b-fieldvalues.tsv` beside them and
  `kd11b-README.md` as the manifest.
- `~/1105rom/derived/proms/` holds the ten 256x4 PROM images per revision, assembled from the
  listing and round-trip verified. They are **not needed by the application** — the loader reads
  the `.tsv`, not a PROM image — so they do not belong in the resources. They are there for
  burning replacement parts, and for the one check that would settle the last two unknowns:
  read an original PROM and diff it against the matching image.
- Carry `kd11b-revision-diff.txt` and `kd11b-corrections.txt` across too. The second is the list
  of nine bits settled by eye; a reader who finds a decode that looks wrong should be able to
  check both lists first.
- The scans themselves stay outside the repository — they are large and they are not the
  artefact. The `.tsv` is the artefact and the README says where it came from.

## Phase 3 — the KD11-B loader

`Kd11bMicrocode.fromListing(resource)` in `pdp11-core` — `fromRoms` is not needed. What it does:

- read the `.tsv`, check it has 214 rows and 40 bits per row;
- check every `LOC` is distinct and below `0400`;
- apply the `NXT XOR 0377` complement and expose the result as `getNextAddress()`;
- decode through the KD11-B field table;
- collect problems rather than throwing, exactly as `Pdp1144Microcode` does — new kinds: wrong
  row count, duplicate address, address out of range, wrong bit count, unresolvable next address.

**The risk this phase carried is gone.** It was the slice map: ten 4-bit slices in the wrong chip
order yield 256 plausible microwords and no symptom. There is no slice map — the listing prints
the assembled word. What replaced it as the dangerous line is the **`NXT` complement**, and that
one is already held down by the 213/214 coverage test, which belongs in the loader's test rather
than in a comment.

Note the loader must tolerate a **sparse** control store: 214 of 256 locations, so `getNextAddress`
can point at a location that does not exist. `A145 @145 -> 377` is the one such case in the
shipped data and it must be a `Problem`, not an exception.

## Phase 4 — annotations, so the window has something to say

**The tags are already here** — all 214 of them, in the `NAM` column of the listing, read from
both scans and checked by the fact that the list sorts exactly in ASCII order. So `SearchBy.TAG`
and the "Symbolic tag" row work for the 11/05 with no extra resource and no flow-diagram reading,
and this phase is no longer the long pole it was expected to be.

What a tag does not give is a *description*. `CCS-1`, `ERT1A`, `SBO-3` name states in a flow the
listing does not print. If a line of prose per microword is wanted, that still has to come from
the microprogram flow diagrams, and it should still be a separate resource that can start empty
and never corrupt the bits. But the window is useful before any of it is written, which it would
not have been from a dump.

## Phase 5 — the window

- `MicrocodePanel`: the declared types become the generic `Microcode`; add a **Microcode** combo
  beside "Search by", listing what can be shown — today `PDP-11/44`, `PDP-11/05 (M7261 rev E)`
  and `PDP-11/05 (M7261 rev F)`.
- **One combo, not two.** A Machine combo plus a Revision combo would leave the second showing a
  single value, or disabled, whenever the 11/44 is selected, and a control that is meaningless
  half the time is worse than a slightly longer list. Three entries is not a list that needs
  splitting; revisit only if a machine with several revisions arrives.
- **The selected revision has to be visible without opening the combo.** The two revisions have
  *identical* addresses and next-addresses and differ in 20 bits across 14 microwords, so a
  wrongly-set revision does not look wrong: every address resolves, every chain walks, and the
  microword you are staring at is simply wrong in `AUX` or `CKO` with nothing to show for it.
  Put it in the window title.
- **The search modes are per machine.** `SearchBy.TAG` works fully for the 11/05 — all 214
  microwords are named — so only `SearchBy.LINE` is the odd one out: there is no source file, and
  a row number in a printed listing is not what anybody is searching for. Filter the combo by
  what the loaded architecture actually offers rather than offering three modes and failing one.
- `showStatus()` prints the symbolic tag unconditionally (`MicrocodePanel.java:405`). Every 11/05
  microword has a name, so this is no longer a gap to fill — but the 42 unlisted control-store
  addresses have no microword at all, and the µPC box can be given one of them off the KM11
  lights. That is the case to handle: "no microword at this address", not "a microword with no
  name".
- `Settings.lastMicrocodeFile` (`Settings.java:70`) becomes per selection, and the selection
  itself persists — somebody who swaps the boards sets this once. Per the settings rule, an
  unknown machine or revision name in the settings file falls back to the default and says so; it
  never stops the app.
- **Optional, and cheap once both revisions are loaded: mark the microwords that differ from the
  other revision.** 14 rows out of 214, in two fields. It is the same vocabulary the memory
  windows already use for a disagreement — colour it and it explains itself — and for somebody
  who owns both boards it turns the window into the thing that says what changed between them.
  `UiColors` gets the constant; do not invent a colour locally.
- Keep one `WindowType.MICROCODE`. The Windows menu is built from what is registered, and a
  second window type buys nothing over a combo. Mark it `multiple` in `WindowType` only if both
  microcodes need to be on screen at once.
- **The printed next-address is only the whole story where `BUT` is `NON`** — 141 of 214
  microwords. In the other 73 the microtest ORs bits into the address, so the printed value is a
  branch *base* and the real successor depends on machine state. The predecessor index and the
  Next button must say so rather than presenting the base as *the* successor; the 11/44 model's
  `BUT ENABLE` handling is the precedent.
- **Retitle, and change what the class says about itself.** The panel Javadoc says "It is a
  reference, not a debugger", because an 11/44's console cannot tell you which microword it is
  executing. **That stops being true here**: with the KM11 in slot 8 the 11/05's µPC is on the
  lights, so `MPC0..7` read off the panel and typed into the µPC box says exactly which microword
  the machine is sitting in. That is the reason to build this, and the documentation should say
  so rather than carrying the 11/44's disclaimer across.

## Phase 6 — proving the slice map is right

Two checks, and both are worth having, because phase 3 has no self-check of its own.

1. **Against the other drawing set.** Already done, and it is what found the revision split.
   Three scans were transcribed independently — the 1973 listing twice, at 815 px and 1460 px,
   and the 1976 listing once. The best 1973 scan and the 1976 scan agree on 99.66% of the 8560
   bits; of the 29 disagreements, 20 are the revision difference and 9 were classifier slips,
   each settled by eye against all three images and recorded in `kd11b-corrections.txt`. This is
   the check that replaced "against the printed listing", because the listing *is* the source.

   It is also the check that says **scan quality is worth spending on**: the 1460 px scan of the
   1973 listing corrects 19 errors in the 815 px scan of the same pages and introduces one.
2. **Against the machine.** The revision question is now settled by reading two PROM part
   numbers, so what is left here is validating the *decode*: the KM11 shows
   `MPC0..MPC7` *and* the control-store outputs on the same connector — `ALU_S0..S3`, `SPAD_0..3`, `CNST`, `AUX_C`, `BUT_*`, `ALUM`, `CIN`, `EALU`,
   `SPWR`. Single-step microinstructions on the real 11/10 and compare the lights against what the
   decoder says microword N asserts. This validates the slice map, the field table and the bit
   positions end to end, against the actual hardware, and it is the project's "a diagnostic must
   be shown the fault it exists to find" rule applied to the thing itself.

Record the result of both in the manifest. A slice map that has been checked against a real
machine and one that has not are different objects and the file should say which this is.

## Phase 7 — tests and documentation

- `Kd11bMicrocodeTest`, mirroring `Pdp1144MicrocodeTest`: **214** microwords, every address
  distinct and below `0400`, 40 bits each, field bit ranges spot-checked against the listing, no
  problems on the shipped data beyond the one expected `A145 -> 377`.
- **The `NXT` polarity test**, which is the one that matters: assert that at least 213 of the 214
  next-addresses resolve to a listed microword. It fails loudly if anyone "fixes" the complement,
  and it is the reason the complement is safe to rely on.
- The chain `B-1 @015 -> B-2 @147 -> B-3 @146 -> BG-1 @040` as a named test — it is readable
  evidence that the field is being decoded the right way round.
- `RS-1` is at address `000`; assert it, as a cheap check that the address column is not shifted.
- `MicrocodePanelTest.java:78` hardcodes the row count as `MicrocodeField.ALL.size() + 4`; it
  becomes the selected machine's table size. Add a case that switches machines and checks the
  table follows, and one that switches *revision* and checks the table does **not** change size —
  same field table, different data.
- **The revision test, which is the one that holds the data down forever**: load both revisions
  and assert they differ in exactly 20 bits across 14 named microwords, all of them in `AUX` or
  `CKO`, and that every address and every next-address is identical between them. That is the
  whole E→F difference expressed as an assertion; if a future re-transcription smears an OCR
  error into the data, this is what catches it.
- `VocabularyTest` — the new combo and its labels go through `labelsOf`.
- `WindowsBuildTest:650` only if a second window type is added.
- `CHANGES.md` entry, per `CLAUDE.md`; `PLAN.md` §6 phase table amended, since it currently
  describes the microcode window as the 11/44's.

## Order of work

Phase 1 is independent of everything else and can be done now. Phase 2 is mostly done and is a
move rather than a task; it gates 3. Phase 4 has collapsed to almost nothing — the tags came with
the bits — so phase 5 no longer has to wait for it or cope with an empty annotation file, and the
window can be finished as soon as 1 and 3 are in. What is left of 6 is the hardware check, which
is the only thing here that needs the machine powered on.

The critical path is now **phase 1**. No decision is outstanding: the revision turned out to be a
user choice rather than something to settle in advance, so nothing is waiting on the bench or on
`EK-KD11B-MM-001`.

## Where this stands

Done, and in the build:

- **Phase 1.** `MicrocodeArchitecture` holds a machine's field table, its next-address field, its
  microtest field, the cross-checks its source document supports and which of its fields are
  don't-cares in which microwords. `MicroInstruction` carries the architecture it was decoded
  against. `Pdp1144Microcode` split into the generic `Microcode` container and the 11/44 listing
  loader; `MicrocodeLineParser` became `Pdp1144LineParser`. `Pdp1144MicrocodeTest` passes
  unchanged in meaning, which is the proof the refactor moved nothing.
  - One thing the plan did not anticipate: **a field had to stop being a bit range**. `SPA` is
    four non-adjacent out-of-order columns and `BUT`/`BRG` are bit-scrambled, so
    `MicrocodeField` now carries an ordered list of bit positions, with `MicrocodeField.of` for
    the ordinary contiguous case. Nothing else could have expressed the KD11-B honestly.
- **Phase 2.** The transcription, the field tables, the revision diff, the corrections list and
  `kd11b-README.md` are in `pdp11-core/src/main/resources/microcode/kd11b/`. The PROM images
  stayed out, as planned.
- **Phase 3.** `Kd11bMicrocode.load(Revision)`, reading only `NAM`, `LOC` and `WORD40` and
  decoding everything else itself. The sparse control store is handled: `A145 -> 377` is one
  `Problem` and not an exception.
- **Phase 5.** The window: the three-entry combo, the revision in the title, the differing fields
  coloured, search modes per document, the decoded next address on its own row, the branch-base
  warning, the don't-care `ALU` field, per-selection settings, and the retitled documentation.
  **It opens on the 11/05 rev F.**
- **Phase 7.** `Kd11bMicrocodeTest` (16 tests) and the additions to `MicrocodePanelTest`. The one
  that matters most is `everyFieldDecodesToWhatTheTranscriptionSaysItDoes`: all 40 bits of all
  214 microwords of both revisions, decoded through `Kd11bFields` and compared against the
  transcription pipeline's own independent decode of the same bits.
